# Ecosystem Memory Map

> Master memory router for ArtisTalks, Artistocks, Zeyoda, and GOSHBOT.
>
> Preserve useful memory. Route every idea through the correct project lens.

---

## Purpose

This map exists so future agents, humans, and GOSHBOT do not confuse the rooms.

The ecosystem has shared DNA, shared language, and shared patterns. That memory should not be deleted. It should be labeled.

When an idea appears in docs, code, chat, or planning, this map answers:

- Is this public ArtisTalks curriculum?
- Is this ArtisTalks technical/app memory?
- Is this a shared pattern from Artistocks or Zeyoda?
- Is this future bridge memory?
- Is this Artistocks-only commerce memory?
- Is this Zeyoda foundation memory?

The rule:

**Preserve shared ecosystem memory, but route it through the correct project lens before suggesting work.**

Shared memory can inspire multiple projects, but every suggestion must be translated through the active project's role.

---

## Canonical Project Roles

### ArtisTalks Teaches

ArtisTalks is the public education, coaching, and preparation app.

It helps artists prepare a release through legacy music-business guidance:

- artist identity
- branding
- colors, logo, font, and visual world
- project planning
- song/story/lyrics reflection
- rights and publishing awareness
- marketing and launch planning
- budgeting and accounting basics
- feedback
- legacy

Public ArtisTalks presents itself as a trusted music-business coach. Crypto, wallet, token, commerce, and web3 concepts are preserved in Artistocks, Zeyoda, or Future Bridge memory.

---

### Artistocks Launches

Artistocks is the separate commerce and launch system.

It handles the store/stage side of the ecosystem:

- stock up
- artist pages
- fan actions
- commerce
- launches
- collecting
- purchases/downloads
- tokens
- testnet/onboarding coins
- future ownership rails

Artistocks may later receive artists who were prepared through ArtisTalks, but public ArtisTalks does not need to mention Artistocks yet.

---

### Zeyoda Protects

Zeyoda is the parent foundation and power system.

It holds the deeper infrastructure:

- security
- auth patterns
- contracts
- APIs
- shared architecture
- system stewardship
- feedback sync
- GOSHBOT/GOSHEESH ops
- long-term sovereignty layer

Zeyoda patterns can inform ArtisTalks, but Zeyoda infrastructure should not be confused with public ArtisTalks curriculum.

---

### GOSHBOT Routes Memory

GOSHBOT is the chief of staff and librarian.

Its job is not to flatten all ideas into one app.

Its job is to say:

> "This note is real, but it belongs in this room."

GOSHBOT should preserve useful memory, identify contradictions, and route work to the right project.

## The Six Memory Rooms

### 1. ArtisTalks Public Memory

This is what the artist can see and experience in the normal public ArtisTalks flow.

Belongs here:

- coaching
- curriculum
- legacy music-business education
- artist identity
- archetype and brand
- mission/gift
- colors, logo, font
- visual world / halo direction
- song/project planning
- lyrics and story
- rights and publishing awareness
- marketing plan
- content plan
- launch/reveal planning
- fan call-to-action in legacy language
- budgeting basics
- accounting sheets
- feedback loop
- legacy reflection

Routed elsewhere:

- Artistocks
- tokens
- wallets
- blockchain
- web3
- swaps
- treasury
- funding
- crypto
- toppins
- commerce rails
- `transferEverything()`

Public ArtisTalks should speak as a music-business preparation guide.

### 2. ArtisTalks Technical Memory

This is how the ArtisTalks app works.

Belongs here:

- Supabase auth
- `profiles`
- `curriculum_answers`
- EmeraldChat
- OrbitPeekCarousel
- ArtisTalksOrbitRenderer
- phase tokens
- active step sync

- answered keys
- inline color/logo/font/asset pickers
- uploads

- technical gotchas
- UX bugs
- app-specific implementation notes

This memory is technical, not public curriculum.

---

### 3. Shared Ecosystem Patterns

This is reusable knowledge that can move between ArtisTalks, Artistocks, and Zeyoda.

Belongs here:

- halo patterns
- orbit patterns
- theme preview patterns
- chat-first UX
- onboarding language
- profile editing patterns
- component lessons
- design lessons
- feedback patterns
- agent workflow lessons
- safety lessons
- naming conventions
- useful architecture ideas that are not product-specific

Shared patterns may inspire multiple projects, but must be translated through the correct project lens.

Example:

- A Zeyoda theme-preview pattern can help ArtisTalks live colors.
- An Artistocks launch lesson can inform ArtisTalks release-prep questions.
- A Zeyoda security rule should not become public curriculum copy.

---

### 4. Future Bridge Memory

This is not current public ArtisTalks.

This is hidden, future, safeword, admin, or advanced-path memory.

Belongs here:

- future Artistocks bridge
- advanced ownership education
- web3 literacy
- contracts ownership education
- artist sovereignty education
- safeword paths
- admin-only pathways
- future readiness checks
- bridge from prepared release to launch system
- behind-the-curtain curriculum

Future bridge memory can be preserved in docs, but should not appear in public ArtisTalks unless intentionally activated.

Routing rule:

If it teaches ownership/web3/Artistocks but should not be public yet, it belongs here.

---

### 5. Artistocks Memory

This belongs to the launch/store system.

Belongs here:

- stock up
- artist pages
- launches
- commerce
- fan actions
- collecting
- tokens
- purchases
- downloads
- testnet
- onboarding coins
- swaps
- asset issuance
- public launch mechanics
- artist/fan transaction flows

If the idea involves commerce or fan transaction behavior, it is probably Artistocks memory.

It should not be added to public ArtisTalks curriculum unless intentionally reframed as non-commerce preparation.

---

### 6. Zeyoda Foundation Memory

This belongs to the parent system and infrastructure layer.

Belongs here:

- security
- auth
- contracts
- APIs
- middleware
- guarded signer
- network guard
- API guard
- feedback sync
- database infrastructure
- parent architecture
- GOSHBOT operations
- GOSHEESH operations
- key and environment safety
- long-term stewardship and sovereignty infrastructure

If the idea involves system safety, contracts, infrastructure, or parent architecture, it belongs here.

## How Future Agents Should Use This Map

Before suggesting work, future agents should ask:

1. Which room does this idea belong in?
2. Is this public ArtisTalks, technical ArtisTalks, shared pattern, future bridge, Artistocks, or Zeyoda?
3. If it mentions money, wallets, tokens, commerce, or web3, is it incorrectly leaking into public ArtisTalks?
4. Can the idea be translated into legacy music-business language for ArtisTalks?
5. Should it remain behind the curtain for now?

Core rule:

**Do not delete useful memory. Route it.**
